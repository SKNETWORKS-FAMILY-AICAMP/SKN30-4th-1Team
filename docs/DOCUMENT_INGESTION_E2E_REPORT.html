대상: backend/pipeline/converters/ 멀티포맷 입력 + 출처 추적 청킹 (PR #1) 환경: MySQL 8.0(docker) · ChromaDB(임베디드) · OpenAI gpt-4.1-mini · PAIM_AUTH_MODE=dev 전처리 규칙은 문서 전처리 정책서, 응답 계약은 API 명세서 참고.

2. 잘 된 것

action 추출이 완전히 안정적이다. 9개 조합 전부 정확히 5건, 담당자 5/5. 양식·포맷·가명화·중첩 어느 축으로도 흔들리지 않았다. 정답과 100% 일치한다.

가명화가 추출에 영향을 주지 않는다. 가명 인물명("참석자 A")도 담당자로 정확히 인식됐다.

빈 파일이 정확히 거절된다. 400 + code: empty_document, detail은 "문서에서 추출된 텍스트가 없습니다." 19자.

변환 경고가 실제 문서에서 의도대로 동작한다. 정형 DOCX는 표 5개 → 경고 5건, 중첩표 문서는 최상위 표 7개 → 경고 7건(중첩 표는 별도 번호를 소비하지 않음), PDF는 반복 머리말 → repeated_line_dropped 1건. 과다 생성 없음.

location이 정확히 붙는다. table 1, table 2, page N 형식으로 R402가 명세에 기록한 내용과 일치한다.

3. 표는 "안 되는" 것이 아니다 — 표별 대조 결과

초판의 판단("표 안의 내용이 추출되지 않는다")은 틀렸다. 숫자만 보고 어느 표에서 무엇이 나왔는지 대조하지 않은 결과다. 정형 문서(03)의 표 5개를 추출된 memory 본문과 문자열 대조했다.

표 내용 추출 판정
표1 회의 정보 회의명·일시·장소·참석 인원 ✗ 정상 — 메타데이터. decision/action/issue/risk 어디에도 해당 없음
표2 참석자 성명·역할·담당 관점 ✗ 정상 — 명단. 카테고리 해당 없음
표3 주요 안건 안건 1~4 ✗ 정상 — 결론이 "잠정 결론" 절에서 decision으로 추출됨. 중복 회피
표4 대안별 검토 기대효과·리스크·판단·후속조치 ✗ 결함 — risk 0건
표5 담당자별 조사 과제 담당·산출물·기한 ✓ 5/5 정상 — owner 5/5, 기한이 content에 포함 
[action] owner=참석자 A  참석자 A가 ... 블루프린트 초안 작성하겠습니다 (~7/28까지).
[action] owner=참석자 E  참석자 E가 ... 대체 도시 2곳 비교하겠습니다 (~7/28까지).

5개 중 3개는 안 뽑히는 것이 맞다. 실제 결함은 표4 하나다.

차이는 표 형식이 아니라 행의 완결성

표5가 되는 이유: 각 행이 그 자체로 완결된 액션이다. 누가 / 무엇을 / 언제까지가 한 행에 모여 있어 MemoryItem(category·owner·content) 스키마에 그대로 대응된다.

표4가 안 되는 이유: 리스크가 열 값으로 흩어져 있다.

[표4] 전통 콘셉트 앨범 | 인지도·확산력 높음 | 섭외·제작비, 전통성 왜곡 위험 | 우선 검토 | ...
                                          ↑ 이 셀이 '리스크'라는 표시가 행에 없음

열 머리글은 첫 행에만 있고 데이터 행은 그 정보를 갖지 않는다. LLM은 이 줄을 "대안 비교표의 한 줄"로 읽는다.

확실하지 않은 부분

  • 표4형을 개선하는 방법 — 평탄화 형식 변경은 효과가 없다는 것만 확인됐다. 열 머리글 부착·마크다운 표로 바꿔도 결과가 동일했다(각 4/4).
  • 정형 문서에서 issue가 0건인 이유 — 정형 문서에 issue에 해당하는 절이 없어 정답 자체가 불분명하다.

5. 깊이 상한 경계 (합성)

Word로 6단 중첩을 손으로 만드는 것은 비현실적이라 python-docx로 생성해 확인했다.

깊이 내용 경고 판정
4단 보존 table_flattened 상한 이내
5단 보존 table_flattened 상한 이내
6단 유실 unsupported_element 유실하되 알림
7단 유실 unsupported_element 동일

경고 메시지: 중첩 깊이 5단을 초과한 표의 내용은 변환되지 않았습니다.

경계는 5/6 사이다. 6단 이상이어도 파일은 정상 업로드된다 — 그 표 내용만 버려지고 문서 전체는 indexed까지 간다.

에러가 되는 것은 깊은 표가 문서의 유일한 내용일 때뿐이다.

깊이5, 표만  → 변환 성공 (5단은 살아남아 블록이 생김)
깊이6, 표만  → 400 empty_document
              "문서에서 추출된 텍스트가 없습니다.
               중첩 깊이 5단을 초과한 표의 내용은 변환되지 않았습니다."

블록이 0개가 되면 assemble()이 오류를 던지되 사유를 메시지에 싣는다. R301과 자체 점검 1번으로 확보된 동작이며, 이번 수정(R401·R501)이 깨지 않았다.

6. 자유 양식의 변동은 LLM 비결정성이다

정형은 안정적이고 자유 양식은 조합마다 결과가 다르다.

dec iss rsk
02 자유 원본 docx 2 0 5
02 자유 원본 pdf 2 1 5
04 자유 가명화 docx 1 5 0
04 자유 가명화 pdf 2 2 3

초판 실행과 비교하면 원인이 드러난다. 코드는 extractor.py·ingestor.py를 전혀 건드리지 않았는데도 분포가 바뀌었다.

초판(c507626) 현재(d73bd04)
01·03 정형 4조합 전부 3/5/0/0 3/5/0/0 ×3, 4/5/0/0 ×1
02 자유 docx 1/5/5/0 2/5/0/5
04 자유 docx 2/5/1/5 1/5/5/0

정형은 두 번 다 거의 동일하고 자유 양식만 크게 흔들린다. 따라서 변동의 원인은 LLM 비결정성이며 포맷 차이나 코드 변경이 아니다.

초판 §7이 "LLM 비결정성인지 PDF 구조 소실인지 분리하지 못했다"고 남긴 질문이 이번 재실행으로 해소됐다.

왜 자유 양식만 흔들리나

원문 자체가 모호하다. "아직 정하지 못한 것"(미결)과 "기억해 둘 위험 신호"(위험)가 둘 다 있는데, 미결 항목은 issue로도 risk로도 분류될 수 있다. 실제로 실행마다 5건이 전부 issue가 되기도 하고 전부 risk가 되기도 했다.

문서를 쓰는 쪽에서 두 범주를 구분해 적지 않는 한 이 변동은 남는다.

7. 포맷 간 구조 차이 (참고)

같은 문서인데 DOCX와 PDF의 블록 구조가 다르다.

blocks heading list_item table_row paragraph
01 정형 docx 63 9 9 28 17
01 정형 pdf 26 0 0 0 26

PDF 변환기는 pypdf로 텍스트만 추출하므로 제목·목록·표 구분이 사라진다. 설계상 그런 것이고 결함이 아니다. 다만 출처 추적의 heading 경로가 PDF에서는 비게 된다(74청크 중 35건만 채움).

정형 문서는 이 차이에도 action 추출이 동일했다(docx·pdf 모두 5/5).

5개 전부 충족. 단 아래 유의사항이 붙는다.

  • 완료 조건의 범위는 **"적재되는가"**이지 "추출 품질"이 아니다. §3·§7·§9의 한계는 완료 조건 항목이 아니며 후속 이슈다.
  • 익명화 실제 회의록 검증은 합성 가명화본으로 대체했다. E 담당자의 실제 산출물이 아니므로 WBS의 해당 항목을 충족한다고 볼 수 없다.
