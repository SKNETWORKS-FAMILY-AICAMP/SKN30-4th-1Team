## 1. 표 4형·중첩 하위 행의 추출 누락 (높음)

**"표가 메모리로 변환되지 않는다"는 서술은 부정확했다.** 빈 DB 재검증(`d73bd04`)에서
표별로 대조한 결과, 표의 형태에 따라 결과가 갈린다.

### 정형 회의록의 표 5개 — 1개만 추출됨

| 표 | 내용 | 추출 | 판정 |
| --- | --- | :---: | --- |
| 표1 회의 정보 | 회의명·일시·장소 | ✗ | **정상** — 메타데이터, 4개 카테고리에 해당 없음 |
| 표2 참석자 | 성명·역할·담당 관점 | ✗ | **정상** — 명단, 카테고리 해당 없음 |
| 표3 주요 안건 | 안건 1~4 | ✗ | **정상** — 결론이 "잠정 결론" 절에서 decision 3건으로 추출됨. 중복 회피 |
| 표4 대안별 검토 | 기대효과·**리스크**·판단 | ✗ | **결함** — risk가 열 값으로만 존재, 0건 추출 |
| 표5 담당자별 조사 과제 | 담당·산출물·**기한** | **✓ 5/5** | **정상** — owner 5/5, 기한 `7/28`까지 content에 포함 |

```
[action] owner=참석자 A  ... 블루프린트 초안 작성하겠습니다 (~7/28까지).
[action] owner=참석자 E  ... 대체 도시 2곳 비교하겠습니다 (~7/28까지).
```

**즉 5개 중 3개는 안 뽑히는 것이 맞고, 실제 결함은 표4 하나다.**

### 차이는 표 형식이 아니라 행의 완결성

**표5가 되는 이유**: 각 행이 그 자체로 완결된 액션이다. `누가 / 무엇을 / 언제까지`가
한 행에 모여 있어 `MemoryItem`(category·owner·content) 스키마에 그대로 대응된다.

**표4가 안 되는 이유**: 리스크가 **열 값으로 흩어져** 있다.

```
[표4] 전통 콘셉트 앨범 | 인지도·확산력 높음 | 섭외·제작비, 전통성 왜곡 위험 | 우선 검토 | ...
                                          ↑ 이 셀이 '리스크'라는 표시가 행에 없음
```

열 머리글은 첫 행에만 있고 데이터 행은 그 정보를 갖지 않는다. LLM은 이 줄을
"대안 비교표의 한 줄"로 읽는다.

### 중첩 표는 상위만 추출된다

`05_중첩표.docx`(3단 중첩) 재검증 결과.

```
상위 표 담당자 5명       → action 5건, owner 5/5   ✓
중첩 표 세부 과제 10여건  → 편곡·녹음·뮤직비디오·쇼케이스 장소·한복 디자이너·관객 동선  전부 ✗
```

중첩 표 행도 `항목 | 조사 내용 | 기한` 구조라 표5형에 가까운데 추출되지 않는다.
**한 블록에 3개 층위가 뒤섞이는 것**이 원인으로 보인다.

```
[표6] 콘텐츠 제작 책임자: 박민재 | 중분류 / 담당 | 세부 내용(3단 표) ; 음원 제작 담당: 정다은 | 항목 | 조사 내용 | 기한 ; 편곡 | 국악 편곡가 섭외 | 7/28 ; ...
```

### 텍스트 전달은 정상이다

변환 단계에서 유실은 없다. 표4의 리스크 문구도, 중첩 표의 `편곡 | 국악 편곡가 섭외 | 7/28`도
`doc.text`에 그대로 있다. **문제는 추출 단계의 인식이다.**

실험으로 확인한 것:

```
중첩 표 텍스트만 (300자)  → action 4/4, owner 4/4 정확히 추출
문서 전체 (3,393자)       → 같은 내용 0건
추출기 청크 수: 1 (분할되지 않음)
```

**평탄화 형식은 원인이 아니다.** 열 머리글 부착·마크다운 표로 바꿔도 결과가 동일했다
(각 4/4). 형식 변경으로는 개선되지 않는다.

### 대상 범위

```
고쳐야 할 것   표4형(속성이 열에 흩어진 표)의 risk·issue
               중첩 표의 하위 행
이미 되는 것   표5형(행이 완결된 액션)
안 뽑는 게 맞는 것  회의 정보·참석자 명단·안건 목록
```

### 가능한 방향 (전부 미검증)

- 표 블록만 별도 추출 패스 — 정확하나 LLM 호출 2배
- 추출 프롬프트에 "표의 각 행을 개별 항목으로 검토" 지시 — 과다 추출 위험
- 청크를 표 단위로 분할 — 위 실험이 사실상 근거를 제공하나 문맥 손실 우려

**왜 이번에 안 했나**: 변환기(담당 C) 영역이 아니다. 텍스트는 완전하게 전달되고
있으며 문제는 추출 단계다.

## 3. 질의 첨부 관대 격리 정책 — `R4B02` 잔여 (중간)

**현재 동작**: 미지원 확장자 첨부는 질의 전체를 `400`으로 중단한다.

**지적 내용**: 다른 변환 실패는 placeholder로 격리해 질의를 계속하는데, 확장자만
예외다. 지원 포맷 첨부가 함께 있어도 답변을 받지 못한다.

**왜 이번에 안 했나**: 4차 대응으로 placeholder 격리를 넣었다가 **되돌렸다.**
그 변경이 예산 우회(`R502`)·명세 드리프트(`R503`)·`sources`/`debug`/인용 계약
확장(`PLAN-01`~`04`)을 연쇄로 만들었다.

7차 자문 결론:

- 명세와 WBS 모두 400 동작을 허용한다
- 미지원 확장자는 "변환 실패"가 아니라 **API가 받지 않는 미디어 형식**이다.
  입력 경계에서 거절하는 것이 정상 정책이다
- 4차 원문도 *"모든 변환 오류를 관대하게 처리하는 계약이라면"*이라는 **조건부** 제안이었다

**바꾸려면 함께 설계해야 하는 것**

```
backend/api/query.py     첨부 루프 재배치 (base64 400·크기 413 검사 순서 보존)
backend/graph.py         attachment_sources 가 sources·debug 두 역할 겸함
backend/retriever/qa_engine.py   SYSTEM_QA의 (출처:) 인용 규칙
docs/API_명세서.md·.html  질의 첨부 정책
docs/HANDOVER_CITATION_FRONTEND.md  인용 대조 계약
```

**담당 D(RAG·인용) 영역과 겹친다.** 단독으로 진행하면 교차 영역 리뷰가 다시 필요하다.

## 4. 변환 실패 첨부의 `sources`·`(출처:)` 의미 (중간)

**증상**: 읽지 못한 첨부가 답변 근거 목록에 **1순위로** 들어간다.

```python
# backend/graph.py:290-292
for source in state.get("attachment_sources") or []:
    if source not in sources:
        sources.insert(0, source)     # 최종 응답 sources 맨 앞
```

지원 포맷이지만 변환에 실패한 첨부도 `(텍스트를 추출할 수 없습니다.)` placeholder와
함께 `sources`에 들어간다. `SYSTEM_QA`는 컨텍스트의 `(출처:)` 값을 복사해 인용하라고
지시하므로, **LLM이 읽지 못한 파일을 인용할 수 있다.**

README의 *"정확도 > 재현율"*, *"출처 있는 답변"* 원칙과 충돌한다.

**왜 이번에 안 했나**: `c507626` 이전부터 있던 기존 동작이다. 3번과 같은 파일들을
건드려야 하므로 함께 설계하는 것이 맞다.

## 5. `last_error` 원시 예외 노출 3곳 (중간)


## 6. 중첩 표 전용 경고 (낮음)

**현재**: 중첩 표가 있어도 경고는 바깥 표 기준 `table_flattened` 하나뿐이다.
**"이 표 안에 표가 더 있었다"는 신호가 없다.**

```
05_중첩표.docx  표 16개(9개 중첩, 최대 3단) → table_flattened 7건
```

내용은 전부 보존되므로 유실은 없다. 다만 사용자가 표 구조가 깊었다는 사실을
알 수 없어, 1번(추출 recall)으로 세부가 누락됐을 때 원인을 짐작하기 어렵다.

**대안으로 검토했다가 기각한 것**: 중첩 표가 있는 DOCX를 아예 거부하기.

- 변환은 정상이다(유실 0). 완전히 변환되는 문서를 막게 된다
- 추출 누락은 중첩 없는 표에서도 동일하게 발생한다 — 거부해도 원인이 남는다
- 국내 업무 문서(예산 내역·결재란·항목별 소계)에서 중첩 표는 흔하다

설계 원칙(*"조용히 버리지 않고 알린다"*)에 맞추려면 거부보다 경고가 맞다.

**왜 이번에 안 했나**: 11라운드째이고 병합 가능 판정을 받은 상태다.
지금 넣으면 검증 라운드가 다시 필요하다.

## 7. `due_date` 컬럼과 추출 정책 연결 (낮음)

**2026-07-30 해결.** `MemoryItem`과 ingestor를 `memory.due_date`에 연결했다.

| 위치 | 상태 |
| --- | --- |
| 연도·월·일이 명시된 절대 날짜 | 원문 구절과 날짜가 일치할 때 자동 저장 |
| 상대·연도 생략 날짜 | 기준일로 단일 후보를 계산해 `set_due_date` 승인 제안 생성 |
| 단일 날짜를 정할 수 없는 표현 | 날짜를 만들지 않고 action `content`에만 보존 |
| 사용자 직접 수정 | 기존 pending `set_due_date` 제안을 자동 거절 |
| 제안 승인 | action 마감 설정 후 memory vector 갱신 |

`date`는 계속 회의·문서 기록일이고 `due_date`는 action 마감일이다. 상대 표현을
자동 확정하지 않으므로 마감 필터의 정확성과 사람 승인 경계를 함께 보존한다.

## 8. `file_too_large` 코드 연결 — `R2B03` (낮음)

변환 실패 400 응답의 최상위 `code`에 `file_too_large`가 추가됐다.
클라이언트가 `code`를 그대로 통과시키고 `detail` 문자열을 표시하므로
**연결 전에도 기존 동작이 깨지지 않는다**(additive).

`code` 값으로 분기하는 로직을 만들 때 반영하면 된다.

## 11. 데스크톱 스모크 테스트 CI 연결 (낮음)

`desktop/scripts/layout-smoke.mjs`(8,571줄)와 `offline-bundle-smoke.mjs`가
`package.json`에 등록돼 있으나 **CI에서 실행되지 않는다.**
`.github/workflows/release.yml`은 태그 push에만 반응하고 스모크 호출도 없다.

수동으로 기억해서 돌려야만 실행되므로, 시간이 지나면 조용히 썩는다.

**필요한 것**: `PAIM_BROWSER_PATH` 환경변수 설정. `BROWSER_CANDIDATES`가 macOS
경로만 하드코딩돼 있어 Linux 러너에서는 이 변수가 필요하다. 스크립트 수정은 불필요.
백엔드 의존 없이 독립 실행된다(API를 스텁으로 처리).

**한계**: 데스크톱 UI 레이아웃 회귀만 잡는다. API를 스텁하므로 백엔드 계약 파손
(예: `R005`)은 잡지 못한다.

**담당**: 프론트엔드. 이번 PR의 리뷰 findings와 무관한 별건이다.
