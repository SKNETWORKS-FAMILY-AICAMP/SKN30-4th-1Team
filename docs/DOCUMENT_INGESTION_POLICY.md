# 문서 전처리 정책서

- 담당: C (멀티모달·Project Memory)
- 최초 작성일: 2026-07-25
- 대상 코드: `backend/pipeline/converters/`, `backend/pipeline/ingestor.py`
- 적용 범위: 업로드 문서(`POST /projects/{id}/documents`)와 질의 첨부(`POST /projects/{id}/query`)

이 문서는 "업로드된 파일이 어떤 규칙으로 텍스트가 되고, 어떻게 잘려서 벡터 저장소에
들어가는가"를 확정한다. 규칙을 바꾸면 기존 색인과 새 색인의 검색 특성이 달라지므로,
변경은 반드시 프로젝트 단위 재색인과 함께 한다.

## 1. 지원 포맷과 우선순위

| 포맷 | 확장자 | 구분 | 상태 | 페이지 정보 |
|------|--------|------|------|-------------|
| 평문·Markdown | `.txt` `.md` `.markdown` | 기존 | 지원 | 없음 |
| Word | `.docx` | **필수** | 지원 | 없음(주 1) |
| PDF (텍스트 레이어) | `.pdf` | **필수** | 지원 | 있음 |
| 한글 | `.hwpx` | 조건부 | 미구현 — 7/25 게이트 통과 후 | — |
| PowerPoint | `.pptx` | 스트레치 | 미구현 | — |
| 음성 전사(STT) | — | 스트레치 | 미구현 | — |

> 주 1: DOCX에는 페이지 개념이 없다. 페이지는 렌더링 시점에 결정되므로 파서가 알 수 없다.
> 페이지 번호를 지어내지 않고 `null`로 두며, 출처 추적은 문단 번호와 제목 경로로 한다.

**포맷 추가 방법**: `backend/pipeline/converters/` 에 모듈 하나를 만들어 `SUFFIXES`와
`convert(filename, data) -> ConvertedDocument`를 선언하고 `__init__.py`의 `_REGISTRY`에
등록한다. 업로드 API·ingestor는 수정하지 않는다 — 지원 확장자 목록의 단일 출처는
레지스트리다.

**명시적 제외(후속 과제)**: OCR·스캔 PDF, 표/차트/이미지의 의미 해석, 화자 자동 매핑.

## 2. 공통 출력 계약 — `ConvertedDocument`

모든 변환기는 원본 포맷과 무관하게 같은 모양을 돌려준다. 후속 단계(extractor·ingestor)는
원본이 무엇이었는지 알 필요가 없다.

```python
ConvertedDocument:
    source:     str                     # 파일명(프로젝트 내부 상대경로)
    format:     str                     # "docx" | "pdf" | "text"
    blocks:     list[Block]
    warnings:   list[ConversionWarning]
    page_count: int | None

Block:
    order:        int                   # 문서 전체 문단 번호 (0부터, 빈틈 없음)
    kind:         "heading" | "paragraph" | "list_item" | "table_row" | "caption"
    text:         str
    page:         int | None            # 1부터. 페이지 개념이 없는 포맷은 None
    level:        int | None            # heading 전용 (1 = 최상위)
    heading_path: tuple[str, ...]       # 이 블록을 감싸는 상위 제목 경로
```

평문 대신 Block 목록을 넘기는 이유는 **출처 추적성**이다. 청킹 시점에 "이 청크가 몇
페이지 몇 번째 문단에서 왔는지" 붙이려면 그때까지 구조가 살아 있어야 한다.

### 보존되는 구조

- **제목**: 레벨과 함께 보존. 하위 블록은 상위 제목 경로(`heading_path`)를 물려받는다.
- **목록**: `list_item`으로 구분. 번호매기기 속성(`numPr`)이나 스타일 이름으로 판정한다.
- **표**: 행 단위로 평탄화하며 셀은 ` | `로 잇고 `[표N]` 접두를 붙인다.
  열 의미는 유실되므로 **항상 경고를 남긴다**. 가로 병합 셀은 python-docx가 같은
  `<w:tc>` 엘리먼트를 반복 반환하므로 **엘리먼트 동일성으로** 접는다 — 텍스트가 같다고
  접으면 값이 우연히 같은 독립 셀(`승인 | 승인`)까지 뭉개져 열 위치가 밀린다.
- **문단 순서**: DOCX는 body XML을 직접 순회한다. `document.paragraphs`만 읽으면
  표가 통째로 사라지고 본문 순서도 깨지기 때문이다.

## 3. 정제 기준

`converters/cleaning.py`에 모두 모여 있다. 포맷별 변환기가 각자 다른 기준으로 다듬으면
청크 품질이 포맷마다 달라지므로, 규칙은 한 곳에만 둔다.

### 3.1 문자 정규화 (`normalize_text`)

| 대상 | 처리 |
|------|------|
| `\r\n`, `\r` | `\n`으로 통일 |
| NBSP(`U+00A0`), 전각 공백(`U+3000`), 탭 | 일반 공백 |
| 제로폭 문자·BOM (`U+200B~200F`, `U+2060`, `U+FEFF`) | 제거 |
| 제어문자 (개행·탭 제외) | 제거 |
| 연속 공백 2개 이상 | 1개 |
| 줄 앞뒤 공백 | 제거 |
| 빈 줄 3개 이상 | 2개 (문단 경계는 보존) |

제로폭 문자는 눈에 보이지 않지만 토크나이저와 중복 비교를 망가뜨리므로 반드시 제거한다.

### 3.2 불필요 정보 제거

**노이즈 줄** (`is_noise_line`) — 본문 의미가 없는 줄을 버린다.

- 빈 줄
- 페이지 번호만 있는 줄: `3`, `- 3 -`, `3/12`, `Page 3 of 12`
- 구분선만 있는 줄: `-----`, `=====`, `＿＿＿`, 박스 그리기 문자 3자 이상

> **알려진 한계**: 숫자만 있는 줄은 연도(`2026`)나 장 번호여도 제거된다. 본문에서 숫자
> 하나가 단독 줄을 이루는 경우가 드물어 감수한다.

**머리말·꼬리말** (`find_repeated_edge_lines`) — PDF 전용.

- 3페이지 이상인 문서에만 적용
- 페이지 **상·하단 각 2줄**만 후보 (위치 제한이 핵심 — 본문에 정당하게 반복되는 문구를
  머리말로 오인해 지우는 사고를 막는다)
- 80자 이하만 후보 (긴 문장은 본문일 가능성이 높다)
- 전체 페이지의 **60% 이상**에 등장하면 제거. 임계값은 `ceil`로 올림한다 —
  내림하면 6페이지 중 3페이지(50%)처럼 기준에 못 미치는 문구까지 지워진다

제거 대상은 삭제하지 않고 **빈 줄로 치환**한다. 통째로 빼면 원본의 문단 경계까지 사라져
서로 다른 문단이 한 덩어리로 붙기 때문이다.

### 3.3 중복 제거 (`drop_duplicate_blocks`)

| 유형 | 기준 | 근거 |
|------|------|------|
| 연속 중복 | 길이 무관 제거 | 변환 과정에서 생긴 잔여물 |
| 전역 중복 | **40자 이상**만 제거 | 반복 고지문·표지 문구 |

40자 미만 짧은 문구(`해당 없음`, `N/A`, `미정`)는 표 안에서 정당하게 반복되므로 전역
중복 제거 대상에서 뺀다. 비교는 공백 정규화 + 소문자 변환 후 수행한다.

경고는 **블록마다가 아니라 개수 요약 1건**으로 낸다(`중복된 문단 N개를 제거했습니다`).
반복 고지문이 있는 평범한 문서에서도 블록당 경고를 내면 수십~수백 건이 쌓여 업로드
응답이 부풀고 정작 다른 경고가 묻힌다. "몇 번째 블록이 중복이었나"는 사용자가 취할
조치가 없는 정보다. 머리말·꼬리말 제거 경고와 같은 형식이다.

**중복 제거 후에도 `Block.order`는 다시 매기지 않는다.** order는 출처 추적의 기준
좌표이므로, 제거 때문에 번호가 밀리면 이미 저장된 인용이 어긋난다.

병합 셀은 python-docx가 같은 텍스트를 반복 반환하므로 행 내부에서 연속 중복 셀을 접는다.

## 4. 청크 크기와 오버랩

| 항목 | 값 | 근거 |
|------|-----|------|
| `CHUNK_SIZE` | **600자** | 기존 ingestor 값 유지. 짧은 청크가 검색 정확도가 높다 |
| `CHUNK_OVERLAP` | **150자** | 문단 경계에서 잘린 문맥을 다음 청크가 이어받는다 |

### 청킹 규칙 (`converters/chunker.py`)

1. **Block 경계를 우선 존중**한다. 여러 블록을 이어 붙이되 `CHUNK_SIZE`를 넘기지 않는다.
2. 단일 블록이 `CHUNK_SIZE`를 넘으면 문장 경계(`. ! ? 。 \n`)로 나눈다.
3. 문장 하나가 그래도 넘으면 `CHUNK_SIZE` 단위로 강제 분할한다.
4. 청크를 확정한 뒤 꼬리 150자를 다음 청크 앞에 붙인다(단어 중간 절단 방지).
5. 오버랩을 붙여 `CHUNK_SIZE`를 초과하면 **오버랩을 버린다**.

오버랩은 문자열로 평탄화하지 않고 **`(조각, Block)` 쌍을 유지한 채** 뒤에서부터 잘라낸다.
마지막 Block 하나에 몰아 귀속하면 오버랩이 여러 블록·페이지에 걸쳤을 때 다음 청크의
`page_start`·`block_start`가 실제 출처보다 뒤를 가리켜, 이 계층의 존재 이유인 출처
추적이 틀린다.

> **불변식**: 반환되는 모든 청크의 길이는 `CHUNK_SIZE` 이하다.
> 회귀 테스트: `tests/test_converters.py::test_chunks_never_exceed_chunk_size`

오버랩 텍스트의 출처는 직전 청크의 마지막 블록으로 귀속한다.

## 5. 메타데이터 스키마

ChromaDB metadata는 `str`/`int`/`float`/`bool`만 허용한다. `None`은 `-1`(정수) 또는
`""`(문자열)로 표현한다.

### 문서 청크 (`item_type = "document"`)

| 키 | 타입 | 설명 |
|----|------|------|
| `project_id` | int | 프로젝트 ID |
| `doc_id` | int | 문서 ID (없으면 `-1`) |
| `repo_id` | int | 리포지토리 ID (없으면 `-1`) |
| `source` | str | 파일명 |
| `item_type` | str | `"document"` |
| `date` | str | 문서 날짜 `YYYY-MM-DD` |
| `doc_type` | str | `meeting` / `planning` / `document` |
| `source_kind` | str | `document` / `repository` |
| `source_type` `source_path` `source_ref` `source_url` | str | 출처 상세 |
| **`source_format`** | str | `docx` / `pdf` / `text` (변환 경로가 아니면 `""`) |
| **`chunk_index`** | int | 문서 내 청크 번호 (0부터) |
| **`block_start`** / **`block_end`** | int | 청크가 걸친 문단 번호 범위 (불명 `-1`) |
| **`page_start`** / **`page_end`** | int | 청크가 걸친 페이지 범위 (불명 `-1`) |
| **`heading`** | str | 청크 첫 블록의 제목 경로 (`상위 > 하위`) |

굵게 표시한 키가 이번에 추가된 출처 추적 필드다.

> **키 집합 불변식**: 구조 정보가 없는 경로(리포지토리 동기화 등)도 **같은 키를** `-1`/`""`로
> 채운다. ChromaDB `where` 필터가 키 유무로 갈리면 같은 질의가 문서 출처에 따라 다른
> 결과를 낸다. 회귀 테스트: `test_ingest_falls_back_to_plain_split_without_converted_document`

### 청크 ID 규칙

- 문서: `doc{doc_id}_chunk{N}`
- 리포지토리: `repo{repo_id}_{source_md5[:6]}_chunk{N}`
- 그 외: `{source_md5[:6]}_chunk{N}`

## 6. 포맷별 예외

### DOCX

- **압축 폭탄 방어**: DOCX는 ZIP이라 업로드 크기 제한(10 MB)이 *압축된* 바이트에만 걸린다.
  반복 텍스트만으로도 압축비 250:1이 나와 10 MB가 2.5 GB로 전개될 수 있다. 파싱 전에
  ZIP 중앙 디렉터리를 검사해 아래 한도를 넘으면 **`file_too_large`** 로 거절한다.
  정상 DOCX의 압축비는 보통 10:1 미만이라 실사용을 방해하지 않는다.
  - 전체 전개 크기 200 MB / 엔트리 1개 100 MB / 전체 압축비 120:1
  - 한도 초과는 `corrupt_file`이 **아니다** — 구조는 멀쩡한 파일이므로 "손상"으로
    안내하면 사용자가 복구·재다운로드 같은 엉뚱한 조치를 하게 된다.
  - ZIP 중앙 디렉터리 자체를 읽지 못하는 경우(`BadZipFile`, 지원 범위를 넘는 extraction
    version, 잘못된 UTF-8 파일명 등)는 `corrupt_file`로 정규화한다. 가드를 넣기 전에는
    `docx.Document()` 주변의 넓은 예외 처리가 흡수하던 입력이라, 여기서 잡지 않으면
    400이어야 할 응답이 500으로 누출된다. 단 `MemoryError` 같은 자원 고갈 예외는
    잡지 않는다 — 입력 오류가 아니라 서버 장애이므로 숨기면 안 된다.
- **중첩 표**: 셀 안의 표까지 재귀적으로 평탄화한다(최대 5단). `cell.text`는 셀의
  **직계 문단만** 이어 붙여 중첩 표가 통째로 사라지므로, 셀 내부를 XML 순서대로 순회해
  `w:p`와 `w:tbl`을 모두 처리한다. 중첩 표의 행은 ` ; `로, 바깥 셀은 ` | `로 구분한다.
  깊이 상한을 넘어 버리는 내용이 있으면 `unsupported_element` 경고를 남긴다.
  이 경고는 **출력 블록이 하나도 없어도 반드시 전달한다** — 상한 때문에 표 내용이
  전부 사라진 경우가 정확히 "조용한 유실"이라 가장 알려야 할 상황이다.
  반면 `table_flattened`(열 구조 유실 안내)는 출력 블록이 있을 때만 의미가 있다.
  두 경고를 한 목록에 섞어 "블록이 있을 때만" 추가하면 전자가 함께 사라진다.
  완전히 빈 표는 애초에 유실 경고를 만들지 않으므로 불필요한 경고가 늘지 않는다.
- 페이지 번호 없음 (`page = None`, `page_count = None`)
- 이미지·차트·도형은 텍스트가 없어 유실 → `unsupported_element` 경고로 개수를 알린다
- 표는 행 단위 평탄화 → `table_flattened` 경고
- 스타일이 삭제된 문서에서 python-docx가 예외를 던질 수 있어 스타일 조회는 방어적으로 처리한다
- 제목 스타일 인식: `Heading N`, `Title`, `제목 N`, `개요 N`

### PDF

- **텍스트 레이어가 있는 PDF만 지원**한다. 스캔 PDF는 `no_text_layer` 오류로 거절한다
- 페이지 단위로 실패를 격리한다 — 한 페이지 추출 실패가 문서 전체를 막지 않는다
- 텍스트가 없는 개별 페이지는 `page_no_text` 경고를 남기고 계속 진행한다
- 암호로 보호된 PDF는 빈 암호로 한 번 시도하고, 실패하면 `corrupt_file`로 거절한다
- **제목을 판별하지 않는다.** PDF는 문단 구조를 보존하지 않아 폰트 크기 추정에 의존해야
  하고, 오판이 `heading_path`를 오염시킨다. 모든 블록은 `paragraph`다
- 빈 줄이 없는 페이지는 문장 종결부호(`. ! ? 。 : ：`) 또는 400자 초과를 문단 경계로 쓴다

### 평문·Markdown

- 인코딩 폴백 순서: **UTF-8 → CP949 → UTF-16**. 국내 문서는 UTF-8 다음으로 CP949가 많다
- UTF-8이 아니면 `decode_fallback` 경고를 남긴다
- 모든 후보가 실패하면 손실을 감수하고 읽되 경고를 남긴다 — 업로드를 실패시키기보다
  사용자가 원본 인코딩 문제를 인지하게 하는 편이 낫다
- ATX(`#`)·Setext(`===`, `---`) 제목, 목록(`-` `*` `+` `1.`), 표(`| ... |`) 인식
- Markdown 표의 정렬 구분행(`|---|---|`)은 내용이 없어 버린다

## 7. 실패 조건과 오류 코드

변환 실패는 전부 `ConversionError`로 통일하고, 업로드 API는 `400`과 함께
`{"detail": "<사람이 읽는 사유>", "code": "<식별자>"}`를 돌려준다.
**조용히 빈 문서로 넘기지 않는다** — 사용자가 "업로드는 됐는데 아무것도 안 나온다"는
상태에 빠지면 안 된다.

> **`detail`은 반드시 문자열이어야 한다.** 데스크톱 클라이언트는 `detail`이 문자열이
> 아니면 사유를 버리고 `"PaiM API 요청 실패"`만 표시한다(`desktop/src/paimApi.ts`).
> 객체로 내리면 "실패 파일은 명시적 오류 반환"이 API 안에서만 참이고 사용자에게는
> 닿지 않는다. 구조화 정보는 최상위 필드(`code`)로 싣는다.

| 코드 | 발생 조건 | 사용자 조치 |
|------|-----------|-------------|
| `unsupported_format` | 등록되지 않은 확장자 | 지원 포맷으로 변환 후 재업로드 |
| `missing_dependency` | python-docx / pypdf 미설치 | 서버 의존성 설치 (운영 이슈) |
| `corrupt_file` | 파일을 열 수 없음, 암호 보호 PDF, ZIP 중앙 디렉터리 손상 | 원본 확인 / 암호 해제 |
| `file_too_large` | 구조는 정상이나 DOCX 압축 해제 크기·압축률 한도 초과 | 문서를 나누거나 내용을 줄여 재업로드 |
| `empty_document` | 추출된 텍스트가 0건 | 내용이 있는 문서인지 확인 |
| `no_text_layer` | PDF 전 페이지에 텍스트 레이어 없음 | 스캔본 대신 원본 PDF 사용 |

**질의 첨부는 예외**: 첨부 변환 실패가 질의 전체를 막지 않는다. 나머지 첨부와 프로젝트
기억만으로도 답할 수 있어야 하므로, 실패 사유를 로그에 남기고
`(텍스트를 추출할 수 없습니다.)`로 대체해 계속 진행한다.

## 8. 변환 경고 형식

경고는 "변환은 성공했지만 원본의 일부가 손실·변형됐다"는 신호다.

```json
{ "code": "table_flattened",
  "message": "표를 행 단위 텍스트로 변환했습니다. 열 구조는 보존되지 않습니다.",
  "location": "table 2" }
```

`location`은 사람이 원본에서 되짚을 수 있는 위치 문자열(`page 3`, `table 2`, `block 17`)이며
해당 없으면 `null`이다.

**중복 제거**: `code`·`message`·`location`이 모두 같은 경고는 한 번만 남긴다. 한 표의 여러
셀이 같은 손실을 겪으면 동일 경고가 수십 건 쌓여 응답이 부풀고 다른 경고가 묻히기 때문이다.
위치가 다르면 서로 다른 경고이므로 그대로 보존된다(예: `page 2`·`page 3`의 `page_no_text`).

**빈 문서일 때의 경고 전달**: 추출된 블록이 0개면 `empty_document` 오류가 나는데, 이때
경고를 그냥 버리면 사용자는 "텍스트가 없습니다"만 보고 원인을 알 수 없다. 표가 문서의
유일한 내용이고 깊이 상한에 걸린 경우가 정확히 그렇다. **경고 메시지를 오류 메시지에
이어 붙여** 사유를 전달한다 — 그러지 않으면 경고를 남기려던 조치가 가장 필요한 상황에서
무의미해진다.

| 코드 | 의미 |
|------|------|
| `page_no_text` | 해당 페이지에 텍스트 레이어 없음(내용 누락) |
| `page_extract_failed` | 해당 페이지 파싱 실패 |
| `table_flattened` | 표를 행 단위로 평탄화(열 구조 유실) |
| `unsupported_element` | 이미지·차트·도형·텍스트 상자가 텍스트로 변환되지 않음, 또는 중첩 표 깊이 상한 초과 |
| `repeated_line_dropped` | 머리말·꼬리말로 판단해 제거 |
| `duplicate_block_dropped` | 중복 문단 제거 (개수 요약 1건, `location` 없음) |
| `decode_fallback` | UTF-8 아닌 인코딩으로 읽음(글자 깨짐 가능) |

**전달 경로**: 업로드 `201` 응답에 즉시 포함한다. 변환은 백그라운드가 아니라 요청 경로에서
수행하므로 폴링 없이 바로 확인할 수 있다. 서버 로그에도 코드 집합을 남긴다.

```json
{ "doc_id": 12, "status": "processing", "format": "pdf",
  "blocks": 87, "pages": 12, "warnings": [ ... ] }
```

## 9. 검증

### 자동 회귀 테스트 — `tests/test_converters.py`

실제 파일 바이트를 만들어 검증한다. 파서를 mock하면 "라이브러리가 실제로 무엇을
돌려주는가"라는 이 계층의 유일한 위험이 검증되지 않는다.

- DOCX: 제목·목록·표 순서 보존, 표 평탄화 경고, 페이지 없음, 빈 문서·손상 파일 거절
- PDF: 페이지 번호 부여, 머리말·페이지번호 제거, 스캔본 거절, 손상 파일 거절
- 평문: Markdown 제목/목록 분류, CP949 폴백, 빈 문서 거절
- 청킹: 크기 불변식, 인덱스 연속성, 페이지 범위 유지, ChromaDB 스칼라 안전성, 내용 보존
- 통합: DOCX 업로드 → ingest 구조 전달, 미지원 포맷·스캔본의 명시적 오류

### 실측 성능 (2026-07-26, 5회 평균)

| 입력 | 크기 | 변환 | 청킹 | 결과 |
|------|------|------|------|------|
| DOCX 50문단 | 35 KB | 14 ms | 0.1 ms | 55 blocks / 13 chunks |
| DOCX 300문단 + 표 5개 | 37 KB | 43 ms | 0.3 ms | 355 blocks / 77 chunks |
| DOCX 1000문단 | 41 KB | 92 ms | 1.5 ms | 1084 blocks / 250 chunks |
| PDF 10페이지 | 24 KB | 28 ms | 0.4 ms | 350 blocks / 44 chunks |
| PDF 50페이지 | 122 KB | 156 ms | 1.7 ms | 1750 blocks / 219 chunks |
| PDF 200페이지 | 491 KB | 555 ms | 6.9 ms | 7000 blocks / 875 chunks |
| TXT 평문 | 1.7 MB | 66 ms | 30 ms | 1213 chunks |

실제 회의록·정책문서는 5~50페이지 규모이므로 **일반적인 사용자 대기시간은 20~150 ms**다.

### 상한 부하 (10 MB 업로드 제한까지)

| PDF 페이지 | 크기 | 변환 + 청킹 |
|-----------|------|------------|
| 600 | 1.4 MB | 1.6 s |
| 1,500 | 3.6 MB | 4.1 s |
| 3,000 | 7.3 MB | 8.4 s |
| ~4,000 | ~10 MB (상한) | **~11 s** |

변환 시간은 페이지 수에 선형 비례하며 pypdf의 텍스트 추출이 지배한다. 위 수치는 폰트
임베딩·스트림 압축이 없는 합성 PDF 기준이라 페이지당 용량이 실제보다 작다. **실제 10 MB
텍스트 PDF는 500~2,000페이지 수준이므로 현실적 상한은 2~5초**다.

> **변환은 요청 경로에서 동기 수행된다.** 변환 경고와 실패 사유를 폴링 없이 즉시 돌려주기
> 위한 의도적 선택이며, 그 대가로 병리적 입력에서 HTTP 요청이 그만큼 블로킹된다.
> 다만 실질적 병목은 아니다 — 뒤따르는 LLM 추출이 같은 문서에서 수 분~수십 분 걸리므로
> 변환 시간은 그에 비해 무시할 수준이다.
>
> 동기 변환이 문제가 되면(리버스 프록시 타임아웃, 워커 점유) 페이지 수 상한을 두어
> 명시적 오류로 거절하는 편이, 변환을 백그라운드로 옮겨 실패 사유 즉시 반환을
> 포기하는 것보다 낫다.

> **DOCX 스타일 조회 주의**: `paragraph.style.name`을 문단마다 읽으면 python-docx가
> 문단마다 기본 스타일을 다시 해석해(`styles.default_for`) 변환 시간의 **84%**를
> 차지한다(1000문단 기준 580 ms → 92 ms, 6.3배 차이). `styleId → 이름` 사전을 문서당
> 한 번만 만들어 쓴다. 새 포맷 변환기를 추가할 때도 같은 함정을 확인할 것.

### 검증 데이터셋 (E 담당자와 공유)

평가계획 기준 세 종류를 혼합한다.

1. 익명화한 실제 조직 회의록
2. 공개 정책·지침 문서 (PDF, 머리말/꼬리말·페이지 번호가 있는 실제 레이아웃)
3. 합성 회의록 및 기존 골든셋

개인정보와 기관 내부 식별정보가 남은 원본은 평가 저장소에 포함하지 않는다.
