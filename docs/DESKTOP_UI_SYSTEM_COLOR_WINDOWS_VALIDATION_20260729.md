# PaiM 데스크톱 UI · 시스템 컬러 · Windows 검증 보고서

- 검증일: 2026-07-29
- 대상 앱 버전: 1.0.4
- 검증 작업 트리: `codex/fix-github-auth-modal-overflow`
- 실제 실행 환경: macOS 26.5.1, Apple Silicon
- 범위: 데스크톱 프런트엔드와 Tauri 앱
- 제외: 백엔드 수정 및 배포

## 1. 결론

요청한 프로젝트 자료 탭 정리는 완료됐다.

- 길게 늘어나던 `파일 추가`를 제목 옆의 짧은 버튼으로 바꿨다.
- `폴더`도 같은 작업 묶음에 배치했다.
- `자료 전체 관리`는 카드 하단으로 내려 목록과 관리 진입의 우선순위를 분리했다.
- 파일 추가, 폴더 추가, 파일 열기·삭제, 전체 관리 패널 열기와 권한 조건은 바꾸지 않았다.

시스템 컬러 점검에서 발견한 네 가지 문제도 수정했다.

- `시스템` 테마의 고대비 보정 누락
- 시스템 라이트 모드의 보조 텍스트 대비 부족
- 작은 프로필 이니셜의 대비 부족
- 강제색 모드에서 선택 탭 표시가 약해질 수 있는 문제

현재 macOS 시스템 설정은 다크 모드이며, PaiM의 `시스템` 테마가 실제로 다크 화면을 선택하는 것을 패키징된 앱에서 확인했다. 설정 화면에서 라이트와 다크를 직접 선택했을 때도 육안상 구조 변화 없이 색이 전환됐다.

Windows용 공개 버전 1.0.4의 CI 빌드와 설치 파일은 존재한다. 다만 현재 작업 트리의 변경사항 자체는 Windows에서 실행하지 못했으므로, 현재 코드를 Windows 배포 준비 완료로 단정할 수는 없다.

## 2. 이번 변경

### 프로젝트 자료 탭

구현 위치:

- `desktop/src/ProjectDetailPage.tsx`
- `desktop/src/styles.css`

변경 내용:

1. 자료 제목과 추가 작업을 같은 헤더에 배치했다.
2. `파일 추가`와 `폴더` 버튼을 내용 폭만 차지하도록 줄였다.
3. 파일 목록은 데스크톱에서 2열, 좁은 창에서 1열을 유지한다.
4. `자료 전체 관리`를 카드 하단 우측으로 옮겼다.
5. 카드 하단에 구분선을 넣어 파일 목록과 전체 관리 진입을 구분했다.
6. Windows 경로도 파일명만 보이도록 `/`와 `\`를 모두 경로 구분자로 처리했다.

실제 패키징 앱에서 `자료 전체 관리`를 눌렀을 때 기존 자료 패널이 열리는 것도 확인했다.

### 채팅 세션 동기화 안정성

기존 기능의 동작을 바꾸지 않고, 늦게 도착한 서버 응답이 로컬 변경을 되돌리는 경합을 막았다.

- 삭제한 세션을 늦은 목록 응답이 되살리지 않도록 삭제 표식을 유지한다.
- 프로젝트별 목록 요청에 세대 번호를 부여해 최신 응답만 적용한다.
- 목록 조회 뒤 세션이 삭제되어 메시지 조회가 404가 되면 그 세션만 제외한다.
- 빠른 연속 이름 변경은 마지막 제목 한 번만 서버에 반영한다.
- 오래된 실패 응답이 최신 성공 뒤 오류 배너를 띄우지 않게 했다.

백엔드는 수정하지 않았다. 현재 배포된 AWS API 계약에 맞춘 프런트엔드 처리다.

자동 검사는 다음도 확인한다.

- 시스템 테마가 OS 라이트·다크를 따라가는지
- 명시적으로 고른 라이트·다크가 OS 설정보다 우선하는지
- `prefers-contrast: more`에서 보조 텍스트가 본문 색으로 강화되는지
- `forced-colors: active`에서 선택된 프로젝트 상세 탭에 2px 윤곽선이 남는지

강제색 검사는 macOS에서 Chromium DevTools Protocol의 `forced-colors` 미디어 에뮬레이션으로 수행했다. Windows 고대비 모드의 브라우저 동작 모델은 검증했지만, Windows 실기기 렌더링을 확인한 것은 아니다.

## 3. 앱 버전과 Windows 확인

### 버전 정합성

다음 네 곳의 버전은 모두 `1.0.4`다.

- `desktop/package.json`
- `desktop/package-lock.json`
- `desktop/src-tauri/tauri.conf.json`
- `desktop/src-tauri/Cargo.toml`과 `Cargo.lock`

설정 화면이 이전 `SKN30-3rd-1Team` 릴리스를 조회하던 오류를 수정했다. 현재 패키징 앱에서 다음 문구를 직접 확인했다.

> 현재 1.0.4 · 최신 v1.0.4

릴리스 페이지 버튼과 최신 릴리스 API가 모두 현재 저장소 `SKN30-4th-1Team`을 사용한다.

### 공개 Windows 1.0.4

[GitHub Actions 실행 `30332793830`](https://github.com/SKNETWORKS-FAMILY-AICAMP/SKN30-4th-1Team/actions/runs/30332793830)을 조회했다.

- 워크플로: `Release desktop installers`
- Windows job: `build-installers (windows-latest)`
- 결과: success
- 공개 릴리스: [`v1.0.4`](https://github.com/SKNETWORKS-FAMILY-AICAMP/SKN30-4th-1Team/releases/tag/v1.0.4)

  - `PaiM-1.0.4-windows-x64-setup.exe`
  - `PaiM-1.0.4-windows-x64.msi`

따라서 태그 `v1.0.4` 기준 Windows x64 설치 파일 생성은 확인됐다.

### 현재 Windows 설정에서 확인된 점

- Tauri 번들 대상은 `all`이다.
- Windows CI는 `windows-latest`에서 x64 MSI와 NSIS EXE를 만든다.
- Windows ICO에는 16, 24, 32, 48, 64, 128, 256px 32-bit 이미지가 들어 있다.
- Windows 릴리스 빌드에서는 별도 콘솔 창을 숨긴다.
- macOS 전용 메뉴 코드는 `cfg(target_os = "macos")`로 분리돼 있다.
- 공통 Rust 파일 읽기 테스트 10개가 통과했다.

### Windows에서 아직 직접 증명하지 못한 점

현재 Mac에는 Windows Rust target과 Windows 런타임이 없다. 아래 항목은 실제 Windows VM 또는 장비에서 확인해야 한다.

1. 현재 작업 트리의 MSI·NSIS 빌드
2. 설치, 업그레이드, 제거
3. WebView2가 없는 환경의 설치
4. 프레임 없는 창의 닫기·최소화·최대화
5. Windows 11 스냅 레이아웃
6. 125%·150%·200% DPI와 다중 모니터
7. SmartScreen 표시

Windows 관련 남은 제품 위험:

- 코드 서명 설정이 없어 SmartScreen 경고 가능성이 높다.
- 자동 업데이트가 없다.
- Windows ARM64 설치 파일을 만들지 않는다.
- Windows 전용 installer 언어·WebView2·다운그레이드 정책이 명시돼 있지 않다.
- 최소 창 크기 `960×680`은 고배율 소형 화면에서 클 수 있다.
- 프레임 없는 투명 창의 Windows 감지가 사용자 에이전트 문자열에 의존한다.

권장 순서는 `PR마다 Windows 빌드` → `코드 서명` → `Windows installer 정책` → `Windows VM UI smoke` → `업데이트 정책`이다.

## 5. 남은 제한과 후속 작업

### 바로 배포를 막지는 않지만 남은 항목

1. 메인 JavaScript 번들이 약 580.57kB라 Vite의 500kB 경고가 남아 있다.
2. 공통 Tauri 창은 투명 배경이며 React 화면이 준비되기 전에 보이면 잠깐 바탕이 비칠 가능성이 있다. 실제 재현은 확인되지 않았고, `page-ready 후 show` 또는 네이티브 배경 동기화 중 하나를 별도 결정해야 한다.
3. CSP가 비활성화돼 있다. 보안 강화 작업에서 별도로 다뤄야 한다.

### 현재 AWS main 계약의 채팅 제한

현재 AWS main의 프로젝트 질의는 프로젝트 RAG와 첨부를 사용하지만 서버 `chat_messages`에 대화문을 저장하지 않는다. 프런트엔드는 현재 배포 계약을 유지하므로 로컬 대화는 보존되지만 서버 영속 대화는 아직 아니다.

나중에 통합 백엔드 PR이 병합·배포되면 다음 작업이 필요하다.

- 새 원자적 query 계약으로 프런트 호출 전환
- 기존 main 호환 분기 제거
- 서버 영속 대화 마이그레이션 확인
- API 계약 회귀와 충돌 재검증
