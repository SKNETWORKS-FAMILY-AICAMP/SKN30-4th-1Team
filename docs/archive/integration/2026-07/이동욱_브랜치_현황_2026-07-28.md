## 1. 요약 (한 줄)

이번 브랜치의 핵심 기능(**문서 기반 액션 완료 판정**)은 백엔드 로직·데이터 보호 측면에서 완성됐고, 코드 리뷰 3라운드를 거치며 **되돌릴 수 없는 데이터 손실 버그 3건**을 찾아 수정·검증했습니다. 다만 **① 프론트가 이 기능을 아직 화면에 노출하지 않고, ② 실제 LLM으로 끝까지 검증하지 못한 상태**라 "기능이 동작한다"를 아직 실증하지 못했습니다. 그 외 리뷰에서 나온 문제 6건 중 1건(git 로그 재업로드 시 데이터 소실)은 제품 의사결정이 필요합니다.

---

## 2. 이번 브랜치가 하는 일

기존에는 회의록·문서를 업로드해도 "지난 액션이 끝났는지"를 시스템이 스스로 알아채지 못했습니다. 이 브랜치는 문서를 적재할 때 LLM이 열린 액션 목록과 대조해서:

- 완전히 끝난 액션 → **완료 제안**
- 액션 일부만 끝난 경우(예: "A, B, C 중 B만 완료") → **N개로 분할하는 제안**

을 만들고, 사람이 승인해야 실제로 반영되는 구조입니다. 관련 커밋 21개 중 다수가 이 기능과 그 주변 안전장치(업로드 동시성, 쿼터, 문서 파괴 방지 등)에 해당합니다.

## 3. 완료된 작업

### 3-1. 핵심 기능 — 문서 기반 완료 판정 (N분할)

- 액션 하나에 sub-task가 여러 개 섞여 있어도(2개 한정이 아니라 N개) 완료분/잔여분을 각각 분리해 반영하도록 구현
- 완료 승인 시 마감일(`due_date`)을 완료 행에는 승계하지 않고 잔여(열린) 행에는 승계하도록 구분
- 완료/잔여 sub-task가 서로 겹치는 경우(LLM 판정 모순) 제안 자체를 생성하지 않도록 가드 추가
- 실제 MySQL 8.0 컨테이너에서 SQL 동작을 직접 검증 (mock 테스트만이 아니라 실 DB 확인)

### 3-2. 데이터 손실 버그 — 3건 발견 및 수정 (치명도 최상위)

| # | 문제 | 재현 방식 | 상태 |
|---|---|---|---|
| 1 | 색인이 이미 끝난 문서가, 그 뒤 부가 단계(완료 제안 생성)의 실패 때문에 **통째로 삭제**됨 | 가드를 일부러 껐다/켰다 하며 삭제 여부가 바뀌는 것까지 확인 | 수정 완료 |
| 2 | 문서 A, B가 같은 액션에 대해 각각 다른 진행 상황을 보고하면, B의 판정이 **조용히 유실**(에러 로그도 없음) | 실제 MySQL에서 재현 — 수정 전 0건 저장, 수정 후 정상 저장 확인 | 수정 완료 |
| 3 | 미완료 상태인 행에 "완료 근거"가 잘못 붙어, 검색 결과가 LLM에게 **모순된 정보**를 전달 | 코드 추적 + 테스트로 고정 | 수정 완료 |

세 건 모두 **실제 실행으로 재현 → 수정 → 재실행으로 해소 확인**까지 마쳤습니다(코드만 읽고 판단하지 않음).

### 3-3. 리뷰 대응 — 후속 4건 수정 (2차 리뷰 기반)

| # | 문제 | 수정 |
|---|---|---|
| 4 | 실패 처리된 문서를 사용자가 삭제할 방법이 없었음 (재시도해도 계속 남음) | 사용자 삭제 경로와 시스템 실패 처리 경로를 분리해 해결. 실제 MySQL로 삭제 확인 |
| 5 | GitHub 연동 시, 하위 항목(이슈/PR 등) 1개만 실패해도 저장소 전체 동기화가 실패 처리됨 | 소스별로 개별 실패를 허용하고 부분 실패를 사용자에게 안내하도록 복원 |
| 6 | 배포용 설정 예시 파일에서 데스크톱 앱 접속에 필요한 값이 누락돼 있었음 | 예시 파일 복원 |

## 4. 코드 리뷰 3라운드 종합 결과

세 번의 독립 리뷰(각각 다른 세션에서 진행)에서 나온 지적을 모두 직접 코드로 재현/반증하며 검증했습니다. 리뷰가 근거 없이 부풀려진 항목은 없었고, 지적된 문제는 실재했습니다.

### 4-1. 이미 처리됨 (위 3-2, 3-3과 동일 항목 다수 포함)

### 4-2. 아직 남은 항목 — 판단·작업 필요

**치명도 높음 — PM 판단 필요**

- **git 로그 재업로드 시 데이터 소실**: git 로그를 다시 올리면 "같은 파일=교체"로 처리되면서 이전 로그에서 뽑아낸 액션·결정 항목이 경고 없이 삭제됩니다. `main` 브랜치에는 없던 동작입니다.
  - 이건 **버그가 아니라 설계 선택의 문제**입니다: git 로그를 "매번 갱신되는 최신 스냅샷"으로 볼지, "누적되는 기록"으로 볼지에 따라 고치는 방향이 달라집니다. **제품 의도 확인이 필요해 보류 중**입니다.

**치명도 중간 — 개발 가능, 순서 조정 필요**

- 로그 기록 중 특정 조건에서 서버가 죽는(크래시) 지점 1건 발견 — 간단한 수정으로 가능
- 업로드 시 권한 확인 순서가 바뀌어, 프로젝트 멤버가 아닌 사용자도 대용량 파일을 서버에 밀어넣을 수 있는 구멍 — 순서만 되돌리면 해결
- 동시에 여러 문서를 처리할 때 데이터베이스 잠금 순서가 뒤바뀌어 있어 드물게 처리 실패가 날 수 있음 — 설계 변경이 필요해 별도 검토 필요

**아직 실증하지 못한 것 (가장 중요)**

- **실제 LLM으로 이 기능이 의도대로 동작하는지 아직 확인하지 못했습니다.** 현재 사용 가능한 API 키가 전부 문제가 있어(쿼터 소진 / 기능 미지원 / 키 미설정) 실제 문서를 업로드해서 "완료 제안이 실제로 생성되는가"를 끝까지 못 봤습니다. 로직상으로는 맞게 짜여 있으나, **LLM이 새로 바뀐 응답 형식을 기대대로 채워주는지는 실행해봐야 아는 부분**입니다.
- **프론트엔드에 이 기능이 아직 노출되지 않았습니다.** 백엔드는 완성됐지만, 데스크톱 앱 화면에 "완료 제안" 카드를 띄우는 작업이 아직 안 들어가 있어 **사용자는 이 기능의 존재를 볼 수 없는 상태**입니다. 프론트 담당자에게 위임 가능한 범위이며 필요한 API 명세는 전달됨.
- 그 외 낮은 우선순위 항목(업로드 속도 제한 정책, 대량 파일 정리 시 성능) 3건은 데모/발표에 당장 영향은 없음.
