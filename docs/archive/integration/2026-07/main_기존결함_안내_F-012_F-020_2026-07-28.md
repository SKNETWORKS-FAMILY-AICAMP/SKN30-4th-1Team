## 1. F-012 — 업로드 본문을 인가 전에 전부 메모리로 읽는다

- **심각도**: High
- **분류**: 가용성 / 자원 고갈
- **위치**: `backend/api/upload.py:276-280`
- **제품 결정 필요 여부**: 없음 — 바로 수정 가능

### 현재 코드

```python
data = await file.read()                                   # 276  본문 전체를 메모리로
if len(data) > _MAX_FILE_BYTES:                            # 277  크기 검사가 read 뒤
    raise HTTPException(status_code=413, ...)
user_id = require_upload_user()                            # 279  인증
require_project_access(project_id, min_role="member")      # 280  인가
```

### 무엇이 문제인가

권한 검사가 본문을 다 읽은 **뒤에** 있습니다. 순서가 뒤집혀 있어 두 가지가 동시에 깨집니다.

**첫째, 비멤버가 자원을 소모시킬 수 있습니다.** `AuthMiddleware`(`backend/main.py:159`)가 무인증 요청은 선제 차단하므로 완전한 외부인은 막힙니다. 그러나 **로그인만 되어 있으면 해당 프로젝트의 멤버가 아니어도** 276행까지 도달합니다. 인가는 280행에나 나옵니다.

**둘째, 크기 상한이 방어 역할을 못 합니다.** `_MAX_FILE_BYTES` 검사(277행)도 `read()` 뒤입니다. 1GB 를 보내면 서버가 1GB 를 임시 파일로 스풀하고 파이썬 메모리에 전부 올린 다음에야 413 을 돌려줍니다. 상한은 "거부 사유"일 뿐 "소비 차단"이 아닙니다.

### rate limit 이 막아주지 않는 이유

```python
# backend/rate_limit.py:16
RATE_LIMIT_UPLOAD = os.getenv("RATE_LIMIT_UPLOAD", "20/minute")
```

SlowAPI 제한은 엔드포인트 래퍼에서 평가되므로 **multipart 본문 파싱 자체를 막지 못합니다.** 분당 20회 이내 요청은 전부 `file.read()` 까지 도달합니다. 계정 하나로 분당 20회 × 대용량이면 메모리·디스크가 고갈되고, 최악의 경우 프로세스가 죽습니다.

### 재현 조건

1. 아무 프로젝트에나 가입된(또는 가입만 된) 계정으로 로그인
2. 자신이 멤버가 아닌 `project_id` 로 `POST /projects/{project_id}/documents` 호출
3. 매우 큰 multipart 본문 전송
4. → 403 이 돌아오기 전에 서버가 본문 전체를 스풀·적재

### 수정 방향

1. `require_upload_user()` 와 `require_project_access()` 를 **`file.read()` 앞으로** 이동. 이것만으로 비멤버 경로가 닫힙니다.
2. 크기 상한을 스트리밍 단계에서 강제. `Content-Length` 만 믿지 말고 chunked 요청도 누적 바이트가 상한을 넘으면 즉시 중단해야 합니다.
3. 가능하면 ASGI/리버스 프록시 계층에도 본문 상한을 둡니다(방어 이중화).

1번은 몇 줄이면 되고 위험이 낮습니다. 2·3번은 별도 검토가 필요합니다.

### 필요한 회귀 테스트

- 인증된 **비멤버**가 초대형 multipart 를 보낼 때, 본문을 끝까지 소비하지 않고 403 을 반환하는지
- 정상 멤버가 상한 초과 파일을 보낼 때, 상한 도달 시점에 중단하고 413 을 반환하는지
- rate limit 초과 요청이 전체 파일을 스풀하지 않는지

## 2. F-020 — git 로그를 다시 올리면 이전 기록이 사라진다

- **심각도**: Medium (데이터 소실이라 실질 체감은 더 클 수 있음)
- **분류**: 데이터 무결성
- **위치**: `backend/api/query.py:201-255`, `backend/quota.py:191-194`, `backend/quota.py:401-414`
- **제품 결정 필요 여부**: **있음 — 결정 전에는 고칠 방향이 정해지지 않습니다**

### 현재 동작

```python
# backend/api/query.py
finalized = finalize_document(reservation["reservation_id"], "git_log.txt", "git")   # 212
...
for old_doc_id in finalized["old_doc_ids"]:                                          # 238
```

모든 git 로그가 **`git_log.txt` 라는 고정 파일명**으로 저장됩니다. 같은 이름의 기존 문서는 `old_doc_ids` 로 수집되고, 새 적재가 성공한 뒤 전부 삭제됩니다. 그 문서에서 추출했던 action·decision 과 벡터도 함께 사라집니다.

### 무엇이 문제인가

git 로그를 **범위를 좁혀 다시 올리면**(예: 최근 100커밋만) 이전 로그에만 있던 항목이 **경고 없이** 지워집니다. 사용자 입장에서는 "최신 로그를 추가했을 뿐"인데 과거 기록이 없어집니다.

애플리케이션 안에 버전·되돌리기·복구 경로가 없습니다. 새 적재가 실패하면 삭제도 일어나지 않으므로 "실패하면 즉시 소실"은 아니지만, **성공한 교체는 되돌릴 수 없습니다.**

### 결정이 필요한 이유

이건 버그라기보다 **설계 선택이 명시되지 않은 상태**입니다. git 로그를 무엇으로 볼 것이냐에 따라 고치는 방향이 정반대가 됩니다.

| 정책 | 의미 | 필요한 수정 |
|---|---|---|
| **교체(현행)** | git 로그는 매번 갱신되는 최신 스냅샷 | 삭제 예정 항목을 사용자에게 사전 고지 + 버전/복구 기간 제공 |
| **누적** | git 로그는 쌓이는 기록 | 고정 파일명을 버리고 commit identity 기반 upsert 로 전환 |
| **교체 + 경고** | 현행 유지하되 위험만 알림 | 업로드 확인 단계에 "N건이 삭제됩니다" 표시 |

현행 동작을 그대로 두더라도 **최소한 사용자에게 알려야 한다**는 점은 세 안 모두 공통입니다.

### 재현 조건

1. git 로그를 업로드해 action·decision 이 추출된 상태를 만든다
2. 더 짧은 범위의 git 로그를 다시 업로드한다
3. → 이전 로그에만 있던 action·decision 이 삭제되고, 사용자에게 아무 안내가 없다

### 필요한 회귀 테스트

이전 로그에만 존재하는 action·decision 을 만든 뒤 축약된 로그를 재업로드하여, **선택한 정책에 맞게** 보존·경고·복구가 이뤄지는지 검증합니다. 정책이 정해지기 전에는 테스트를 확정할 수 없습니다.
