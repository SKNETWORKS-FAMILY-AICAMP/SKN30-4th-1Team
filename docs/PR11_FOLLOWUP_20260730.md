## 2. 결론

PR #21은 PR #11의 저장소 동기화 generation 정합성 계약을 보존한다. 사용자가 동기화를 실행하면 기존 게시 세대를 유지한 채 새 세대를 준비하고, 완성된 세대만 원자적으로 게시하며, 늦게 끝난 worker의 결과가 현재 세대를 덮지 못하게 한다.

반면 다음 두 항목은 동일하게 보존되지 않았다.

1. 연결된 GitHub branch의 원격 HEAD와 마지막 색인 SHA를 비교해 `최신 / 최신화 필요 / 확인 필요 / 확인 실패`를 보여주는 사용자 기능
2. 문서 converter registry를 업로드·질의·capabilities의 확장자 단일 기준으로 자동 사용하게 하는 구조

두 항목의 성격은 다르다.

- 원격 최신성 확인은 현재 사용자 동작에 직접 영향을 주는 기능 누락이다.
- converter registry 연동은 현재 지원 포맷에는 장애가 없으며, 향후 포맷 확장 시 여러 파일을 함께 고쳐야 하는 확장성 회귀다.

GitHub 연동을 시연 범위에 포함한다면 원격 최신성 확인은 후속 브랜치에서 포팅하는 것을 권장한다. converter 단일 기준화는 변경량이 작으므로 같은 후속 작업에 포함하는 편이 좋지만, 시연 전 새 포맷을 추가하지 않는다는 조건으로 명시적 제외도 가능하다.

## 4. 누락된 GitHub 원격 최신성 동작

### 4.1 PR #11의 의도

서버의 `indexed` 상태는 “마지막 동기화 작업이 성공했다”는 뜻이지 “현재 GitHub 원격 HEAD와 동일하다”는 뜻은 아니다. PR #11은 다음 두 값을 분리했다.

- `commitSha`: 서버가 마지막으로 성공적으로 색인한 commit SHA
- `remoteHeadSha`: 연결된 GitHub branch의 현재 HEAD SHA

두 SHA를 비교해 다음 상태를 계산했다.

| 상태 | 의미 | 사용자 동작 |
| --- | --- | --- |
| `current` | 마지막 색인 SHA와 원격 HEAD가 같음 | 추가 동작 없음 |
| `needs_sync` | 원격 HEAD가 바뀜 | 동기화 실행 |
| `checking` | 원격 HEAD 조회 중 | 완료 대기 |
| `unknown` | 유효한 비교 결과가 없거나 캐시 만료 | 다시 확인 |
| `error` | GitHub 조회 실패 또는 App session 만료 | 재시도 또는 재인증 |

SHA 비교는 대소문자를 정규화하고 full SHA와 abbreviated SHA의 prefix 일치도 허용했다.

### 4.2 5분 캐시의 정확한 의미

PR #11은 5분 고정 polling을 하지 않는다. 이벤트가 발생할 때만 확인하고, 5분 이내의 최근 시도 결과를 재사용한다.

| 이벤트 | 동작 |
| --- | --- |
| GitHub 패널 진입 | 캐시가 만료됐으면 branch 기준 activity와 HEAD 갱신 |
| 앱 창 focus 복귀 | 캐시가 만료됐으면 `per_page=1` HEAD만 조회 |
| 저장소 동기화 완료 | activity와 HEAD를 강제로 갱신 |
| 사용자의 `다시 확인` | 캐시를 무시하고 HEAD를 즉시 재조회 |
| GitHub 조회 실패 | 실패 시각도 기록해 focus 연속 발생 시 즉시 재요청하지 않음 |
| 5분 경과 | 기존 성공을 계속 `최신`으로 표시하지 않고 `unknown`으로 만료 |

관련 구현:

- `b3e9627:desktop/src/github.ts:119-185`
- `b3e9627:desktop/src/App.tsx:3880-3912`
- `b3e9627:desktop/src/App.tsx:7440-7772`
- `b3e9627:desktop/src/GithubPanel.tsx:424-485`

실패 상태에서 이전 성공의 `remoteCheckedAt`을 보존하더라도 `error`가 우선하므로, 오래된 성공 결과를 `최신`으로 광고하지 않는다. 수동 재시도는 `force` 옵션으로 캐시를 우회한다.

### 5.2 실제 사용자 영향

1. 사용자가 저장소를 연결하고 한 번 동기화한다.
2. 이후 팀원이 GitHub에 새 commit을 push한다.
3. 서버의 published generation은 안전하게 이전 SHA를 유지한다.
4. 앱은 원격 HEAD가 바뀐 사실을 확인하지 않으므로 사용자에게 알리지 않는다.
5. 사용자는 검색과 Project Memory가 이전 SHA 기준인지 알 수 없다.
6. 사용자가 추측으로 동기화 버튼을 누르면 최신 generation으로 안전하게 전환된다.

즉 데이터 손상이나 세대 혼합 문제는 아니다. 문제는 stale 상태의 발견과 설명이 사용자에게 제공되지 않는다는 것이다.

추가 영향:

- GitHub timeline은 최초 연결 시점 데이터에 머물 수 있다.
- 앱 focus 복귀로 최신성을 확인하지 않는다.
- 원격 조회 실패와 session 만료를 “마지막 성공과 구분된 최신성 상태”로 표시하지 못한다.
- 서버에서 non-default branch로 연결된 저장소는 UI activity와 서버 색인 branch가 달라질 가능성이 있다.
- 항상 보이는 동기화 아이콘이 우회책이지만, 사용자는 언제 눌러야 하는지 판단할 근거가 없다.

일정상 가능하지만 제품 계약을 명확히 축소해야 한다.

필수 조건:

- GitHub 연동은 “사용자가 필요할 때 항상 수동 동기화”하는 기능으로 정의
- 앱이 remote HEAD 최신 여부를 보장하거나 표시하지 않는다고 명시
- GitHub timeline의 자동 최신화를 보장하지 않음
- non-default branch의 activity 표시는 MVP 보장 범위에서 제외
- 시연 전 새 문서 converter를 추가하지 않음
- PR #11 종료 댓글에 제외 항목과 수동 동기화 우회책을 명시

일반적인 “#21로 완전히 대체됨”만 남기고 종료하는 것은 실제 코드 상태와 맞지 않는다.
